## What fixed it

fastp 3' quality trimming. The portal uses `--cut_tail` at fastp defaults
(window 4, mean Q20), not mean Q15:

    fastp --trim_poly_x --cut_tail --qualified_quality_phred 15 --length_required 50

Checked three ways: the fastp read count equals the portal's STAR input
(19,715,741); the trimmed length is identical for 100% of reads (compared
against the reads recoverable from the portal's mapped and unmapped BAMs);
and STAR unique/multi counts match exactly.

## Remaining residual: read order (explained 2026-09-26)

UMI dedup differs from the portal by a few reads per sample, all among
multi-mappers, so about 0.1% of genes differ, by 1-5 reads. The cause is
read order, not anything we can match:

1. With several threads, STAR writes its unsorted BAM in whatever order its
   threads finish, which changes from run to run.
2. `samtools sort` keeps that order for reads at the same position.
3. Among duplicates that tie, UMICollapse keeps the first in file order. For
   a multi-mapped read, the copy kept decides which gene gets the count.

Evidence: two runs of the same FASTQ (this `reproduce_portal.sh` run and
the first `run_pipeline.sh` run, 2026-09-26) produced sorted BAMs with
identical alignments in a different order at tied positions. Their counts
differ by up to 2 reads, and their dedup multi-mapper totals by up to 18
reads (sample 2: -10 vs -28 against the portal).

Consequences:

- The portal's residual cannot be removed; its read order came from its
  own STAR threads and is not recorded anywhere.
- Our own runs can be made reproducible. `scripts/02_align.sh` now uses
  `--outSAMorder PairedKeepInputOrder` (reads in FASTQ order; SAM output
  piped to `samtools view`). On a test sample, 16 and 4 threads gave
  byte-identical sorted BAMs, with the same alignments and STAR statistics
  as default output. On the full LJQQSK samples, two runs (32 and 16
  threads) gave identical STAR statistics, dedup BAM records and counts.
- The acceptance test (`validation/compare_to_portal.py`) therefore
  requires STAR statistics to match the portal exactly, allows a small
  tolerance after dedup, and requires a repeat run to be identical.

## Exact recipe (all verified)

- Reference: Ensembl GRCm39 release 114 primary assembly + ERCC92
  (`data/reference/`); @SQ matches the portal exactly.
- fastp 0.24.0: as above.
- STAR 2.7.11b: defaults + `--outFilterIntronMotifs RemoveNoncanonical
  --outSAMattributes NH HI AS nM NM MD --outSAMtype BAM Unsorted
  --outReadsUnmapped Fastx`, then `samtools sort`.
- UMICollapse: `bam --umi-sep _` (UMI follows the last `_` in the read name).
- featureCounts (subread 2.1.1): `-t gene -g gene_id -s 1 -M --fraction`.
  CPM = count / total * 1e6.

## Status (2026-09-26)

The recipe is now the pipeline default (`run_pipeline.sh` + `scripts/`),
with these additions:

- STAR reads are written in FASTQ order (see above).
- UMICollapse uses a 64 GB Java heap; the bioconda wrapper's 4 GB default
  ran out of memory on full-size samples.
- RSeQC gene body coverage runs on 2,803 housekeeping genes
  (`scripts/make_housekeeping_bed.py`), about 10 minutes per sample instead
  of hours on the full gene model. This does not affect counts.
